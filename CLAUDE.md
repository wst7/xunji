# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

寻迹 · Xunji (Save anything. Find it by memory.) is a personal link collection and recall tool: save a URL, and a background worker fetches it, extracts the article, summarizes and indexes it. Later, a natural-language description retrieves the original from the user's own collection and explains why it matched.

- `docs/PRODUCT.md` — product positioning, principles, scenarios and scope.
- `docs/ENGINEERING.md` — engineering contract: API paths, database DDL, module signatures, status/error enums. Backend, API, database and frontend sections are authoritative.

## Commands

### Docker (whole stack)

```bash
docker compose up --build
# app http://localhost:3000 · landing http://localhost:3001 · API http://localhost:8000
```

### Backend — run from `backend/`

```bash
uv venv --python 3.12
uv pip install -e '.[dev]'
.venv/bin/python -m app.db --migrate
.venv/bin/python -m uvicorn app.main:app --port 8000     # API
.venv/bin/python -m app.workers.runner                   # worker, separate terminal
.venv/bin/python -m app.workers.runner --once            # process at most one job
```

Tests use a real PostgreSQL database, not mocks:

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m pytest tests/test_search.py::test_chinese_full_sentence_query -q
XUNJI_TEST_DB=xunji_test_search .venv/bin/python -m pytest -q   # parallel-safe database
```

`tests/conftest.py` sets `DATABASE_URL` to `xunji_test` before importing app modules, creates the database if missing, runs migrations, and truncates all business tables between tests. The local PostgreSQL role/database must exist and provide `vector`, `pg_trgm`, and `pgcrypto`. There is no backend lint or format script configured.

### Frontend — run from the repository root (npm workspaces)

```bash
npm install
npm run api:typecheck
npm run dev            # app on 5173
npm run dev:landing    # static landing page on 5174
npm run build          # tsc + vite for web, then builds landing
```

If port 8000 is occupied by another API: `XUNJI_API_TARGET=http://127.0.0.1:8010 npm run dev`. There is no frontend test runner or lint script; `tsc` (strict, `noUnusedLocals`) during `npm run build` is the type check.

### Mobile app — `apps/mobile` (standalone iOS + Android, Expo)


## Architecture

### Backend runtime

FastAPI and the worker are separate processes sharing the same code. The API saves a document and enqueues a `processing_jobs` row; the worker claims jobs with `FOR UPDATE SKIP LOCKED`. PostgreSQL is both the database and the persistent queue (lease, retry with backoff, active-job dedupe, stale-job reclaim). Saving returns immediately — parsing and indexing are always asynchronous.

Request flow: `app/api/*` → `app/services/*` → `app/parsers/*` / `app/ai/*`. The worker drives `app/ai/pipeline.py::process_document`, which moves a document through `fetch → parse → summarize → chunk → embed → index` and updates `parse_status` / `parse_stage`.

Failure semantics: `partial` means metadata was saved but body extraction was incomplete; `failed` keeps the document row and original URL. A failed remote summary falls back to the extractive provider so chunking/indexing still completes; embedding failures remain retryable. Content is never invented and document rows are never deleted on failure. Reprocessing is idempotent and reuses an active job. Deletes are hard deletes with cascades.

The backend is **synchronous** SQLAlchemy 2.0 (`psycopg` v3); do not introduce async sessions.

### Search

`app/services/search_service.py` performs four-way recall in PostgreSQL — full-text, pg_trgm similarity, literal term matching, and pgvector chunk similarity — normalizes each channel within the candidate set, and combines them with configurable weights. Queries are cleaned of Chinese narrative/question filler and indexed fields include title, summary and body, so a remembered summary alone can recall a document. No model is called at query time; indexes are prebuilt. `match_reason` must be assembled only from real evidence (matched channel, matched terms, source), never generated. Every query is scoped by the authenticated `user_id`; cross-user access returns 404.

### Data and configuration invariants

- Migrations in `backend/migrations/*.sql` are applied in order by `app/db.py::run_migrations()`, recorded in `schema_migrations`, and must be idempotent. `{{EMBEDDING_DIM}}` is substituted with `EMBEDDING_DIM`. The API also runs migrations on startup.
- `EMBEDDING_DIM` must equal the provider's actual dimension; mismatches abort startup by design.
- Default `AI_PROVIDER=extractive` and `EMBEDDING_PROVIDER=local` are real offline implementations — no external key is needed for a full local run.
- Remote AI is vendor-neutral: `openai` and `openai-compatible` both mean any OpenAI-compatible Chat Completions / Embeddings service. Base URL, path, auth header/prefix, extra headers, JSON mode and timeout are configuration (`app/ai/openai_compat.py`); do not add provider-specific branches for individual vendors.
- `source_type`, `parse_status`, and parse error codes appear in the DDL/contract (`docs/ENGINEERING.md`), `packages/shared/src/index.ts`, and UI label maps (`packages/shared/src/format.ts`). Change them together; backend schemas currently type them as plain `str`.
- Auth: bearer tokens are stored server-side as SHA-256 hashes. All user-data queries must filter by `user_id`.

### Frontend

React 19 + Vite + react-router-dom, no component library and no CSS framework. The whole visual system lives in `apps/web/src/styles.css` (warm-paper palette, serif headings, rust accent, hairline lists). Do not reintroduce Tailwind or a component library. Markdown is rendered by a custom restricted renderer (`components/Markdown.tsx`); raw HTML is never injected.

`packages/api/src/index.ts` provides `createApiClient` (`@xunji/api`): path/query building, bearer injection, the 15s timeout, `{data}` unwrapping, error-envelope parsing, and the 401 callback shared by both clients. The adapters in `apps/web/src/api/client.ts` and `apps/mobile/src/api/client.ts` only supply the base URL, token access and platform 401 side effects. `/health` is the only endpoint returning a bare object; `DELETE` returns 204. Status polling (`LiveStatusBadge`) runs every 1.5s only for non-terminal documents and stops at `completed | partial | failed`.

`packages/shared/src/index.ts` holds the API contract types consumed by both clients; `format.ts` / `errors.ts` hold platform-neutral labels and helpers (`STATUS_TEXT`, `statusTone`, `isTerminalStatus`, `domainOf`, date formatting, URL extraction, `ApiError`, friendly messages). Web and mobile must both import from `@xunji/shared`; do not fork these maps. Keep the contract aligned with `backend/app/schemas.py`.

### Mobile app — local-first, no login

`apps/mobile` is a standalone Expo / React Native app (iOS + Android) that stores everything on the device. It does **not** call `/api/v1`, has no accounts, and needs no backend running. The web app and backend stay in the repo for self-hosting and future sync, but the app is independent of them. Expo Router has no tab navigator: `components/AppTabBar.tsx` provides the 首页 / 收藏 / 我的 bottom bar on the three top-level screens (`router.replace`); detail and share are pushed screens.

- `src/local/db.ts` opens SQLite (`expo-sqlite`, file `xunji.db`) with WAL, the `documents` table and `settings`. The schema deliberately keeps `updated_at` and tombstones deletes via `deleted_at` so multi-device sync can merge by timestamp later; `documents_url_active_idx` is a partial unique index on `url WHERE deleted_at IS NULL`.
- `src/local/pipeline.ts` is the on-device worker: single-flight `processPendingQueue()` (≤20 per pass, triggered on boot, save, focus, foreground and manual retry) drives `fetch → parse → summarize → save`, updating `parse_status` / `parse_stage` exactly like the backend contract.
- `src/local/article.ts` fetches with a 25s abort and extracts heuristically (meta tags, `<article>`/`<main>`/`<body>`) — no DOM library. `src/local/repo.ts` owns all SQL plus local search: Chinese bigrams + Latin words, weighted title/keywords/summary/body/site scoring, `match_reason` built only from real hits.
- No model is required. `src/local/llm.ts` optionally calls the user's own OpenAI-compatible `chat/completions`; base URL and model live in AsyncStorage, the API key **only** in `expo-secure-store` (`xunji.llm.key.v1`) and is never logged. Without it, summaries are extractive. The same adapter backs the settings screen's 测试连接.
- System share uses `expo-share-intent` (iOS Share Extension, Android `ACTION_SEND`), so it only works in a development build, not Expo Go. `ShareIntentBridge` skips it in Expo Go. The native payload is reset before any async save, then `/share` saves locally and replaces to the detail screen.
- UI lives in `apps/mobile/src` (screens, components, theme), with thin route files in `app/`. `theme.ts` is a **deliberately separate** mobile design language (cool-neutral canvas, white cards, indigo accent, system sans) — it does not mirror `apps/web/src/styles.css`, and changing one does not require changing the other. Markdown uses an RN restricted renderer, never a WebView or raw HTML.
- Development builds permit arbitrary HTTP (ATS exception / cleartext) because the app fetches pages directly; production builds are HTTPS-only. `EMBEDDING_DIM`, auth, and other backend invariants are unchanged for the backend.

### Deployment

**Web deployment is paused.** The product is the local-first mobile app; `apps/web` and `backend/` remain for local development and self-hosting, but no workflow deploys them.

The landing page is a separate static site — it is not part of the app; its Docker build injects `XUNJI_APP_URL` into `__APP_URL__` and `XUNJI_SITE_URL` into `__SITE_URL__` (for the absolute `og:image`) at build time, and its real product screenshots live in `apps/landing/public/shots/`. `.github/workflows/pages.yml` builds it and deploys to GitHub Pages at `https://wst7.github.io/xunji/`; `apps/landing/vite.config.ts` sets `base: './'` for project-site paths, and the CTA points at the GitHub releases page for the APK. **GitHub Pages on the Free plan requires a public repository** — if the repo stays private the workflow cannot enable Pages; host `apps/landing/dist` elsewhere (Cloudflare Pages / Netlify) instead. The mobile app is not part of Docker Compose; it ships through Xcode / Android Studio / EAS Build, and its share extension requires a development build.

`northflank.json` (repo root) is a Northflank v1.2 template that deploys the stack from GitHub: project, PostgreSQL 16 addon, a backend build service, the API and worker as separate services from the same image, and the web app as the only public service. Only `apiVersion` and `spec` are allowed at the top level. Secrets are generated (`${fn.randomSecret}`) or injected from the addon (`POSTGRES_URI` aliased to `DATABASE_URL`); never commit real keys into it. The web service proxies to `http://xunji-api:8000` via `API_UPSTREAM`. The landing page is deliberately not in the template. Procedure and post-deploy checks: `docs/DEPLOY_NORTHFLANK.md`.

`deploy/free/Dockerfile` is the free-tier counterpart: one container runs uvicorn, the worker (`backend/start-all-in-one.sh` backgrounds it and reaps it if the API exits) and serves the built SPA. `app.main::_mount_spa` mounts `/assets` and a catch-all only when `XUNJI_WEB_DIR` is set, so every other deployment mode is unchanged; `api/*` under the fallback still returns the JSON `NOT_FOUND` envelope. `render.yaml` wires that image into a Render free web service (external Supabase PostgreSQL, `WORKER_POLL_SECONDS=15`). `get_engine()` sets `prepare_threshold=None` for psycopg URLs so pgbouncer transaction poolers (Supabase/Neon) work. Runbook and limits: `docs/DEPLOY_FREE.md`.

`.github/workflows/android.yml` builds an installable arm64 release APK on GitHub (prebuild + `assembleRelease`, Node 22 and JDK 17, path-filtered on `apps/mobile` and `packages`). It needs no repository variables — the app is fully local. It builds with `APP_VARIANT=production` (HTTPS-only). The APK is signed with the template's debug key and is not store-ready.

Both the API (`app/main.py` lifespan) and the worker (`app/workers/runner.py::main`) run migrations at startup, because a managed platform may start the worker first and `run_once` touches tables immediately. `run_migrations()` holds a transaction-scoped advisory lock so concurrent starts serialize instead of racing on DDL. When the landing page is hosted where the domain is only known after deploy, build with `XUNJI_RUNTIME_URLS=1` to keep the placeholders and let `apps/landing/docker-entrypoint.d/40-xunji-urls.sh` substitute them at container start.
